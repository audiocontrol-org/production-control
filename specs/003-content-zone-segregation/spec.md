# Feature Specification: Content zone segregation

**Feature Branch**: `feature/voice` (long-lived; spec resolved via the CLAUDE.md SPECKIT marker, not the branch)

**Created**: 2026-07-25

**Status**: Draft

**Design record**: `docs/superpowers/specs/2026-07-25-content-zone-segregation-design.md` (design-approved on roadmap node `design:feature/content-zone-segregation`)

**Originating item**: surfaced while designing `design:feature/voice-editions`; this feature blocks it. Related backlog: **TASK-15** (a separate *safety* dependency, not a feature dependency — see FR-024).

## Overview

production-control distinguishes three content classes, already latent in its graph:
**human-authored** (authored nodes), **mechanically-generated** (derived nodes with a
*pure* provider), and **AI-generated** (derived nodes with an *impure* provider). Nothing
today keeps them apart on disk: a human can be handed AI-generated bytes sitting in the
area they treat as their own authored workspace, and nothing refuses it.

This feature enforces strict segregation so the three never blur, by **directory-naming
convention**, and makes the segregation **legible to a human from the path alone**. The
load-bearing rule: AI (impure) output may never be written to a human-safe path. The
convention is chosen because a person reads a file's zone at a glance — in a file tree, a
`git status`, a diff — with no tooling. The machine reads the same fact from the graph's
impurity flag; enforcement keeps the two views from ever contradicting each other.

The feature adds only **routing, build-time enforcement, and an audit verb**. It
introduces no new node kind and does not change the graph (Constitution Principle VI).

## The four invariants (the principle, above the mechanism)

- **INV-1 — Structural segregation (bidirectional for the two hard classes).** Human-authored
  content MUST reside in a human-safe path; impure-derived content MUST reside in an
  AI-permitted path; pure-derived content MAY reside in either.
- **INV-2 — Human legibility at a glance.** A person MUST be able to tell from a path alone —
  no tooling, no manifest lookup, no graph query — whether a location is **human-safe** or
  **AI-permitted**. A dot-zone means *AI-permitted / not human-safe*, **not** "definitely AI":
  pure or operational files may live there too.
- **INV-3 — The two channels never diverge.** The path (human channel) and the graph's
  impurity flag (machine channel) are two projections of one fact and MUST agree in both
  directions: an impure node may not resolve into a human-safe path, and an authored node may
  not resolve into an AI-permitted path.
- **INV-4 — No in-place takeover of impure artifacts.** No supported workflow may require or
  legitimize a human editing an AI-generated artifact in place; human work creates a *separate
  authored node* (the manifest's existing advisory "is a response to" edge). This is a
  workflow guarantee, not a claim that such an edit is mechanically impossible.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - AI output can never land in a human's working area (Priority: P1)

An operator builds an impure (AI) target. The system writes its bytes only to an
AI-permitted location and refuses, naming the path, if anything would put impure bytes into
a human-safe area — including via a mis-declared provider or a symlink. The operator can
trust that no file in a human-safe path was AI-generated.

**Why this priority**: This is the safety core and the MVP. With only the build-time refusal
plus correct routing, the load-bearing invariant (INV-1/INV-3, impure direction) holds and
the feature already delivers its central value. Everything else strengthens legibility and
earlier detection.

**Independent Test**: Configure an impure target and confirm its output is routed under a
dot-zone and accepted; then force impure output toward a dot-free path (directly, via a
provider that declares pure but returns impure, and via a symlink whose real target is
human-safe) and confirm each is refused, naming the path. No other class of node need be
involved.

**Acceptance Scenarios**:

1. **Given** an impure target, **When** it is built, **Then** its output is written under an
   AI-permitted (dot-zoned) path and accepted.
2. **Given** an impure output whose resolved path is dot-free (human-safe), **When** the
   build runs, **Then** it is refused and the message names the offending path.
3. **Given** a provider **declared pure** that returns an impure result, **When** the build
   runs, **Then** it is refused — a pure declaration may not become impure at runtime after
   routing has already chosen a human-safe location.
4. **Given** an impure output that is a symlink whose lexical path is dot-zoned but whose real
   target resolves into a human-safe path, **When** the build runs, **Then** it is refused —
   classification is evaluated on the resolved destination, not the lexical path.
5. **Given** a provider that returns a path escaping its assigned output directory, **When**
   the build runs, **Then** it is rejected as a containment/escape violation **before** zoning
   is evaluated, regardless of the provider's impurity.

### User Story 2 - A person can read any file's zone from its path alone (Priority: P2)

Anyone scanning the repository — a file tree, a diff, a pull request — can tell whether a
location is human-safe (safe to author in) or AI-permitted, without running anything. Human
content and AI content are never intermixed in one directory subtree in a way that misleads.

**Why this priority**: Human legibility is a first-class safety channel (INV-2), not a
convenience. It also completes the bidirectional guarantee: authored content is kept out of
AI zones (INV-3, authored direction) so the path never tells a human a location is unsafe to
author in while the graph calls it authored.

**Independent Test**: Apply the zoning rule to a set of representative paths by inspection and
confirm each resolves to exactly one zone as specified; confirm an authored node routed into a
dot-zone is refused and an authored node in a human-safe path is accepted.

**Acceptance Scenarios**:

1. **Given** any path relative to the production root, **When** its zone is determined, **Then**
   it is AI-permitted if and only if at least one of its parent directory segments begins with
   `.`; otherwise it is human-safe.
2. **Given** a dot-prefixed *file* (e.g. `dist/.draft.md`) in a directory whose segments are all
   non-dot, **When** its zone is determined, **Then** it is **human-safe** — the basename does
   not establish a zone.
3. **Given** an absolute path whose ancestors *above the production root* contain a dot-directory
   (e.g. a repository `.git/`), **When** zoning is determined for content inside the production
   root, **Then** those outside ancestors do not affect the result.
4. **Given** an authored node routed into a dot-zone, **When** the build/validation runs, **Then**
   it is refused (INV-3, authored direction); an authored node under a human-safe path is accepted.
5. **Given** dot-directories with different semantic names (`.cache`, `.tmp`, `.ai`), **When**
   their zone is determined, **Then** they are treated **identically** as AI-permitted — `.ai`
   is conventional, not special.

### User Story 3 - Zoning violations are caught before a build, with an honest scope (Priority: P3)

An operator runs a read-only audit over the manifest and learns whether any target's *routing*
would violate zoning — before spending a build — and the audit is explicit that runtime
filenames and provider escapes are only checkable at build time.

**Why this priority**: Earlier, cheaper detection of a configuration mistake. It depends on the
enforcement (US1/US2) existing and is strictly additive; it never replaces the build-time
refusal, which remains the actual integrity boundary.

**Independent Test**: Point the audit at a manifest containing a correctly-routed set and confirm
it passes; introduce a target whose assigned output location is not dot-zoned (impure) or is
dot-zoned (authored) and confirm the audit reports it, naming the target, while stating plainly
what it did not check.

**Acceptance Scenarios**:

1. **Given** a manifest whose every impure target routes to a dot-zone and every authored node to
   a human-safe path, **When** the audit runs, **Then** it passes.
2. **Given** a manifest with an impure target whose assigned output location is dot-free, **When**
   the audit runs, **Then** it reports that target as a routing violation, naming it.
3. **Given** any audit run, **When** it reports, **Then** it states that provider runtime
   filenames and provider escape are verified only at build time, not by the audit.

### Edge Cases

- A pure provider output written into a human-safe area (a generated README, a YAML) is
  **permitted** — the (pure-may / impure-must-not) asymmetry (FR-005).
- A directory-valued impure output is classified from its **root path**; all files it contains
  inherit that zone. (Interacts with `design:feature/directory-outputs`; see Dependencies.)
- A human opens and edits an impure artifact in a dot-zone anyway → the node still becomes
  `modified`. This feature does **not** protect those bytes; it only makes such editing
  unsupported and conspicuous (FR-024, INV-4).
- A dot-zone that holds a pure or purely-operational file (`.cache/…`) → still human-legible as
  *AI-permitted / not human-safe*; the path does not assert the file *is* AI-generated (INV-2).
- A path with no dot segment anywhere → human-safe by the fail-safe default; a missing mark
  never silently exposes an area to AI.

## Requirements *(mandatory)*

### Zoning rule

- **FR-001**: The system MUST classify every path, relative to the supplied production root, into
  exactly one zone: **AI-permitted** iff at least one of its **parent directory** segments begins
  with `.`; otherwise **human-safe**. The classification MUST be total and require no configuration.
- **FR-002**: Only **directory** segments MUST establish a zone. A dot-prefixed **basename** in an
  otherwise non-dot directory MUST NOT make the path AI-permitted.
- **FR-003**: Only segments **at or below the production root** MUST participate. Dot-directories in
  the absolute path *above* the production root MUST NOT affect classification of content inside it.
- **FR-004**: The default MUST be fail-safe: a path with no dot-prefixed directory segment is
  human-safe. Absence of a mark MUST leave an area protected, never exposed.

### The segregation invariant

- **FR-005**: Impure-provider output MUST resolve to an AI-permitted path. Pure-provider output MUST
  be permitted in either zone (a mechanically-generated file MAY live in a human-safe area).
- **FR-006**: Authored content MUST resolve to a human-safe path; a dot-zone MUST NOT be a supported
  authored workspace (INV-1/INV-3, both directions for the two hard classes).
- **FR-007**: The build root `dist/` MUST remain usable as-is; impure artifacts MUST be written to a
  dot-prefixed subdirectory somewhere under it. No rename of `dist/` is required or performed.

### Enforcement (fixed order; defense-in-depth)

- **FR-008**: The system MUST **route** an impure target's assigned output location into a dot-zone,
  and an authored node's into a human-safe path, so the correct — and human-legible — placement is
  achieved by construction.
- **FR-009**: For each declared output the build MUST, in this order: (a) resolve the path; (b) reject
  traversal/escape; (c) confirm the **symlink-resolved** destination is **contained** within the
  assigned output directory; (d) evaluate zoning; (e) stage. A path escaping the assigned directory
  is a general contract violation caught at (b)/(c) **regardless of impurity** — zoning MUST NOT be
  the sole defense against escape.
- **FR-010**: Zoning MUST be evaluated on the **resolved (real) destination**, not the lexical path. A
  symlink whose lexical path is dot-zoned but whose real target is human-safe MUST be refused.
- **FR-011**: A contained impure output resolving to a dot-free (human-safe) path MUST be refused, and
  the refusal MUST name the offending path (Constitution Principle V — fail loud, name the cause).
- **FR-012**: A provider **declared pure** MUST NOT return an impure result. Runtime impurity metadata
  MAY corroborate a statically-declared impure provider, but MUST NOT introduce impurity a pure
  declaration lacked; a build that sees runtime-introduced impurity on a pure declaration MUST refuse.
  (This closes the false-safe path where a pure declaration is routed to a human-safe location and the
  provider only then announces impurity.)

### The audit verb

- **FR-013**: The system MUST provide a read-only **routing audit** over the manifest that reports any
  impure target whose assigned output location is not dot-zoned, and any authored node whose location
  is not human-safe, naming each.
- **FR-014**: The audit MUST report its scope honestly: it verifies **routing policy** only, and MUST
  state that provider runtime filenames and provider escape are checked at build time, not by the audit.
- **FR-015**: The audit MUST be read-only, MUST offer machine-readable output, and MUST exit 0 when
  clean and non-zero when it finds a violation (gate semantics; Constitution — read verbs `--json`, exit 0;
  gates exit non-zero).

### Legibility and semantics

- **FR-016**: All dot-prefixed directories MUST be treated identically as AI-permitted; no dot name
  (`.ai`, `.cache`, `.tmp`) is special. Documentation and messages MUST convey the asymmetric meaning:
  *dot-zoned → AI-permitted / not human-safe*; *non-dot → not impure / human-safe*.
- **FR-017**: v1 MUST NOT define a standalone file-type or role enforcement layer. Directory and file
  **names** are the single human-legibility surface; the graph's impurity flag is the machine authority;
  any further type/role check is explicitly reserved and unspecified (a non-goal, not a silent omission).

### Scope, provenance, and lifecycle boundaries

- **FR-018**: This feature MUST NOT introduce a new node kind and MUST NOT change the artifact graph. It
  adds routing, enforcement, and an audit verb over the existing authored / pure-derived / impure-derived
  distinction (Constitution Principle VI).
- **FR-019**: Impurity MUST continue to be sourced from the existing provenance channel (the provider's
  static impurity declaration, corroborated but not introduced at runtime per FR-012). No new provenance
  field is required.
- **FR-020**: An AI artifact MUST remain a valid, reproducible build product for its whole life. The
  existence of a separate human-authored companion MUST NOT demote it; which node is a release target is a
  manifest declaration, not something this feature imposes.
- **FR-021**: A directory-valued impure output MUST be classified from its root path, with every contained
  file inheriting that zone.

### Fail-loud and honesty

- **FR-022**: Every refusal in this feature (zoning, escape, runtime-impurity) MUST name what is wrong and
  which path/target it concerns. There MUST be no silent skip and no fallback that masks a violation
  (Constitution Principle V).
- **FR-023**: Documentation and any surfaced messages MUST NOT claim the path identifies *exact* provenance;
  the path answers "is this location human-safe or AI-permitted," and the graph answers "what produced this."

### Safety boundary with TASK-15

- **FR-024**: This feature MUST NOT claim to protect the bytes of an in-place edit to an impure artifact.
  An accidental edit still yields a `modified` state, and TASK-15 (build has no state guard; the
  stale-over-modified precedence can silently erase a hand edit) remains a **separate safety dependency**.
  The feature's safety story MUST state this distinction wherever described: zoning makes such editing
  unsupported and conspicuous; it does not protect the bytes.

### Key Entities

- **Zone**: one of `human-safe` or `AI-permitted`, derived deterministically from a path relative to the
  production root (FR-001).
- **Production root**: the directory supplied to production-control against which paths are made relative
  and zoning is evaluated (FR-003).
- **Content class**: the existing node classification — authored / pure-derived / impure-derived — whose
  machine-side impurity signal must agree with the path's zone (INV-3).
- **Routing decision**: the assigned output location for a target, chosen so its class and its zone agree
  by construction (FR-008).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Across any manifest and any build, **zero** impure-provider artifacts come to rest at a
  human-safe path — every attempt is refused, naming the path.
- **SC-002**: **100%** of paths under the production root are classifiable into exactly one zone by
  inspection of the path alone, with no tooling, and the classification matches the normative rule
  (FR-001–FR-003) including the basename, above-root, and identical-dot-name cases.
- **SC-003**: **Zero** authored nodes come to rest in an AI-permitted path — each such routing is refused.
- **SC-004**: A provider declared pure that returns an impure result is refused in **100%** of cases,
  before its bytes are accepted into any human-safe location.
- **SC-005**: A symlinked output whose real target is human-safe is refused in **100%** of cases; zoning is
  never satisfied by a lexical path alone.
- **SC-006**: The routing audit detects **every** routing-policy violation present in a manifest (no
  false-clean) and reports its own scope limits explicitly in every run.
- **SC-007**: Every refusal produced by the feature names the offending path or target; there are **zero**
  silent skips or masking fallbacks.
- **SC-008**: The feature is delivered with **no** new node kind and **no** change to the artifact graph
  (verifiable by inspection of the graph model surface).

## Assumptions

- A production root is supplied to production-control, and manifest/provider output paths are relative to
  it (consistent with the existing relative-path handling).
- The graph already exposes each node's class and each provider's static impurity declaration; this feature
  reads them, it does not invent them.
- Pure providers may legitimately write into human-safe areas (a generated README, a YAML), as the operator
  affirmed; the asymmetry is intentional (FR-005).
- The existing atomic stage-then-commit build path is retained; enforcement runs before staging (FR-009).

## Dependencies

- **Blocks** `design:feature/voice-editions` — a voice edition is AI-generated prose and this feature is
  what keeps it out of a human's working area; that record depends on this one.
- **TASK-15** (`build-destroys-hand-edits-without-refusing`) — a **safety** dependency, not a feature
  dependency (FR-024). This feature functions without it, but the repository MUST NOT claim derived edits
  are protected until TASK-15 is fixed.
- **`design:feature/directory-outputs`** — a directory-valued impure output is a dot-zoned *tree* (FR-021);
  the interaction is noted so it is not discovered late. This feature does not depend on directory-outputs
  landing first.

## Out of scope (explicit non-goals, not silent cuts)

- A standalone **file-type/role enforcement** layer (FR-017 reserves it, unspecified).
- A **`resolve-edit` verb** or any resolution of the `modified` state for pure outputs — overlaps TASK-15
  and is tracked there.
- A fourth **`machine-operational`** storage zone (`.production/`, `.cache/`, `.work/`) — captured in the
  design inbox as `machine-operational-storage-zone`; watch, do not build now.
- The mechanics of **directory-valued outputs** themselves (`design:feature/directory-outputs`).
- **Fixing TASK-15** — a separate item; this feature only states the boundary (FR-024).
